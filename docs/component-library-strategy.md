# 组件库战略：从手工作坊到生产线

> 版本：V0.1 ｜ 日期：2026-08-18 ｜ 状态：用户认同（决策记录）
> 背景：2026-08-18 提纲挈领评价——机制层已领先、内容层仍在手工作坊；本文件是把该判断沉淀为组件库发展的战略基线。
> 关联：`domains/yuhong/plans/component-library-blueprint-V0.1.md`（内容蓝图）——本文件是"怎么生产"，蓝图是"生产什么"。

## 1. 项目本质判断

**组件库不是素材库，是"判断的算法库"。** 每个组件 = 一个可复用的判断单元（教学问题 → 输入 → 输出 + 视觉表达），把"顾问会做但说不清"的方法变成"谁都能执行、执行了能验证"的资产。

- 价值标准：每个组件能否独立完成一次完整的教学/业务判断，而不是"有多少页"；
- 失败判据：组件没接住判断 = 判断落空（"无源页页面无根"即此）；
- 项目护城河（product-architecture 已有定义）：机制——引导模式、防伪条款、组件契约、验收闭环、两 Agent 分工；护城河不在内容。

## 2. 现状的三个结构性矛盾（2026-08-18 诊断）

### 矛盾一：组件库没有单一数据源
一套组件散在五处：`decision-component-store.md`（卡片）、`interactive-course-components.md`（互动卡）、`component-slots.json`（合同）、`catalog.json`（注册表）、`component-index.json`（索引）。加一个组件 = 手工改五处 + 渲染 + 图册。DC-05 走一遍踩了两个坑（PS5.1 中文注释、BOM），边际成本肉眼可见。**内容在增长，生产方式仍是手工作坊。**

### 矛盾二：四套资产割裂，没有"组件类型"维度
决策卡 13、互动卡 8、可执行源页 8、分析卡 20+，各自为政。"决策组件"统称掩盖了诊断 / 互动 / 共创 / 收尾四种完全不同的教学任务类型——互动类恰是课件最需要、最没落地的一层（I1-I8 全部无源页）。

### 矛盾三：扩容是"补漏"逻辑，不是"环节闭环"逻辑
按决策流列缺项（DC-16、DC-06、I1…），但每个决策环节需要"诊断 + 互动 + 输出"组件组合才能完成教学。只补一个诊断组件，环节仍是断的。

## 3. 合理扩充路径（生产线四步）

```
1. 立"单一数据源"：新建 component-registry.json 统一登记全部组件
   字段：类型（诊断/互动/共创/收尾）｜决策环节｜模块｜教学问题｜输入｜输出｜
       不变式｜源页｜槽位合同｜预览
   图册 / 索引 / catalog / 组件卡全部【从注册表生成】——写生成器，不再手工同步五处
   → 扩一个组件从"改 5 处"变成"改 1 处 + 跑生成器"

2. 类型作为第一维度（用户已拍板）：先做 I1 互动样板（课件价值所在）；
   诊断类组件模板化程度高、可批量

3. 按"决策环节闭环"扩充，不按"缺啥补啥"：
   每个环节定义完整教学需要的组件组合（诊断 + 互动 + 输出），按闭环扩

4. 组件门禁：每个组件必须答出 4 问才能进库——
   教学问题？输入？输出/决策？不变式？答不出的不进库
```

## 4. 组件门禁（进库标准）

每个组件入库前必须回答：

| 问 | 判据 |
|---|---|
| 教学/管理问题 | 一句话说清"这页让学员/老板判断什么" |
| 输入 | 需要哪些数据/素材；缺了怎么标注（低置信度代理/待验证） |
| 输出/决策 | 学员/老板完成后带走什么判断或动作 |
| 不变式 | 哪些标签、语义、结构固定不可改（如四力、三杠杆、四阶段名） |

答不出任一问 → 不进库；已进库的组件也按此门禁回检。
